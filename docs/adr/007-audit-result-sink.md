# ADR 007: 결과 감사는 로컬 로테이션 후 오브젝트 스토리지로 best-effort 업로드한다

- Status: Accepted
- Date: 2026-08-17
- 관련: 000, 001, 006

## 문제

확정된 LLM 결과 이벤트(요청당 1레코드, 프롬프트·응답 본문 포함)를 다운스트림 분석·조사 파이프라인이 쓸 수 있게 보관해야 한다. 초기 구현은 NATS JetStream으로 보존했다.

JetStream은 상태를 가진 브로커라 운영 의존성이 크다 — 스트림 프로비저닝, 계정·권한, 보존/중복창 설정, 그리고 게이트웨이가 살아 있으려면 브로커도 살아 있어야 한다. 감사 데이터는 대부분 "올라가면 좋고, 못 올라가도 치명적이지 않은" 성격인데, 그 데이터를 위해 무거운 stateful 의존을 얹는 게 균형이 맞지 않았다.

## 결정

**감사 sink는 로컬에 로테이션 로그를 쌓고, 백그라운드에서 오브젝트 스토리지로 best-effort 업로드한다.** 외부 무빙파츠는 오브젝트 스토리지 하나뿐이고, 그마저 배포 컴포넌트가 아니라 *라이브러리*(minio-go)로 붙는다.

**로컬 3단계 + 원자적 핸드오프.** `active/`(쓰는 중) → `pending/`(봉인, 업로드 대기) → `uploaded/`(업로드 완료, 보관 중). 봉인은 `active`를 fsync 후 `pending`으로 `rename`하는 것 — 같은 파일시스템의 원자적 rename이 writer와 shipper의 유일한 접점이라, shipper는 "쓰는 중인 파일"을 절대 보지 않는다. 로테이션은 시간(기본 1시간)과 크기 두 트리거로 건다.

**객체 키는 시간 파티션 + 인스턴스 유일성.** `s3://<prefix>/dt=YYYY-MM-DD/hour=HH/<pod>-<sealTS>-<rand>.jsonl`. 파드 이름(downward API `POD_NAME`)이 레플리카 간 유일성을 보장해 분산 시퀀서가 필요 없다. 랜덤 접미사는 **봉인 시점에 한 번 고정**되고 파일명이 곧 객체 키라, 크래시로 업로드·삭제 사이가 끊겨 재시도해도 같은 키를 덮는다(멱등). dt/hour 파티션은 DuckDB/Athena류가 열지 않고 프루닝하게 한다.

**best-effort, 유실 허용.** PVC를 강제하지 않고, per-write fsync 대신 봉인 때만 fsync한다(앱 크래시엔 페이지캐시가 생존, OS 크래시의 버퍼 손실은 허용). 요청 경로는 절대 막지 않는다 — 쓰기는 공유 `AsyncSink` 뒤에서 일어난다([ADR 001](001-component-boundaries.md)). 디스크 상한을 넘으면 이미 업로드된 파일부터, 그다음 오래된 pending부터 버린다(bounded loss).

**업로드와 로컬 삭제는 분리한다.** 업로드 주기와 별개로, 업로드 후 로컬 보관 기간(retention)이 지나야 reaper가 지운다. 최근 파일이 로컬에 남아 재처리·디버깅에 바로 쓰인다.

**버킷은 미리 존재해야 한다 — 앱은 만들지 않는다.** 시작 시 존재를 확인해, 확실히 없으면 부팅을 실패시킨다(오퍼레이터가 프로비저닝하도록). 스토리지가 일시적으로 안 닿는 경우엔 경고만 하고 진행한다 — 일시 장애가 게이트웨이를 막지 않고 업로드는 복구 후 재시도한다.

**NATS를 제거하지 않고 공존시킨다.** 감사 sink와 NATS publisher는 각자의 설정으로 독립 활성화되고, 둘 다 켜지면 이벤트가 양쪽으로 fan-out된다. 기존 NATS 소비자를 유지한 채 감사 경로를 점진 도입하기 위함이다.

### 경계선

- **오브젝트 스토리지는 로그 검색 저장소가 아니다.** Loki 같은 관측용 저장소는 라벨만 인덱싱해 큰 본문·레코드 분석에 안 맞는다. 감사 데이터는 전용 버킷에 파티션된 JSONL로 두고, 검색이 필요하면 분석 엔진을 따로 얹는다.
- **무손실이 필요하면** 배포 시 audit 디렉토리에 PVC를 붙이면 된다 — 설계는 그것에 의존하지 않지만 배제하지도 않는다.
- 수집 에이전트(Promtail/Fluent Bit)를 쓰지 않는다 — 에이전트 자체가 또 하나의 운영 의존성이라, 자기 로그를 자기가 싣는 단일 바이너리를 택했다.
- **레코드는 프롬프트·응답 본문을 평문 그대로 담는다.** 조사(pmap)·재처리가 1차 용도라 본문이 필요하고, 지금은 레닥션을 넣지 않는다 — 접근은 버킷 ACL과 보존기간으로 통제한다. 필드 단위 레닥션/마스킹은 후속 결정으로 미룬다.

## 근거

- 상태는 오브젝트 스토리지에 위임하고 컴퓨트는 단순하게 — 클러스터의 Loki가 이미 같은 철학(단일 바이너리 + S3)으로 도는 산 증거다. 감사도 같은 MinIO를 버킷만 달리해 재사용한다.
- 봉인 시점 고정 키가 멱등성을 코드가 아니라 이름 규칙으로 보장한다.
- fan-out으로 공존시키면 전환에 절단면이 없다 — NATS를 끄는 건 나중의 독립된 결정이 된다.

## 결과

- 업로드되기 전 pending/active는 파드가 다른 노드로 리스케줄되면 로컬 디스크와 함께 유실될 수 있다(PVC 미사용 시). 유실 상한은 로테이션 주기 + 업로드 랙 + 디스크 상한 정책으로 묶인다.
- 버킷이 없으면 부팅이 실패한다 — 의도된 것(만들지 않는다는 계약). 대신 오퍼레이터가 버킷을 선프로비저닝해야 한다. 스토리지가 일시적으로 안 닿는 경우는 예외로, 경고만 하고 부팅을 진행한다(일시 장애가 게이트웨이를 막지 않도록).
- **S3 장기 장애 시 pending이 디스크 상한까지 쌓이다 오래된 것부터 조용히 버려진다** — best-effort·유실 허용 데이터라 의도된 것. 표면화는 별도 지표가 아니라 로그(업로드 실패 경고 + 드롭 카운터)로 하고, 관측/알람은 그 로그를 기준으로 운영한다([메트릭은 보류, 로그 위생 우선] 기조와 일치).
- **본문을 평문으로 보관**하므로 버킷 접근통제·보존기간이 유일한 방어선이다 — 필드 레닥션은 후속 PR에서 다룬다.
- 종료 시 fan-out은 자식 sink을 순차로 닫는다 — 최악 지연이 `Σ(AsyncSink CloseTimeout) + FileSink 최종 flush(15s)`까지 늘 수 있으니, `terminationGracePeriodSeconds`를 `ShutdownDrainTimeout + 이 합 + 여유`로 잡는다.
- 둘 다 켜면 이벤트가 두 경로로 나가 벤더/브로커 부하가 중복된다 — 전환기의 의도된 비용.
- 다운스트림은 dt/hour 파티션과 요청당 1줄 JSONL을 계약으로 받는다 — 스키마가 바뀌면 이 계약도 함께 관리해야 한다([ADR 006](006-cassette-e2e.md)의 픽스처 규율과 같은 맥락).
