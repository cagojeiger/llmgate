# ADR 009: 감사 파이프라인 스케일 하드닝 — 시간버킷·압축·병렬 업로드

- Status: Accepted
- Date: 2026-08-17
- 관련: 007, 008

## 문제

[ADR 007](007-audit-result-sink.md)의 3단계 파이프라인(active → pending → uploaded)을 부하 관점에서 점검하니 몇 가지 천장이 드러났다.

- **업로드 주기 기본 1h + DiskCap 5Gi** → 무손실 지속 처리량이 `DiskCap/UploadInterval ≈ 1.4 MB/s`로 묶였다(저볼륨 튜닝).
- **disk-cap 검사도 업로드 주기(1h)에 묶여** 있어, 그 사이 고트래픽이면 물리 디스크가 먼저 찰 수 있었다.
- **업로드가 단일 고루틴·순차** → 레플리카당 업로드 천장이 단일 스트림 처리량이었다.
- 로테이션이 크기 위주라, 파일이 임의 시각 경계에 걸려 **나중에 시간 단위로 분석하기 불편**했다.

## 결정

**시간 버킷을 1급 로테이션 트리거로.** active 파일은 `RotateInterval`에 정렬된 **클록 경계**(예: 매시 정각, 또는 10분 경계)에 봉인된다 — 한 파일 = 한 시간창 = `dt/hour` 파티션 한 칸이라, 파일 커버리지가 한눈에 보인다. `RotateMaxBytes`는 **안전판**으로만 남아(단일 객체 폭주 방지), 정상 부하에선 시간이 트리거다.

**압축 단계 추가.** pending → compressed 로 넘길 때 gzip(표준 라이브러리, 새 의존성 0)으로 압축한다. 객체키는 `.jsonl.gz`. 감사 JSONL은 반복 스키마 + 텍스트라 압축이 잘 먹혀, **디스크·업로드 두 천장을 함께 밀어올린다**(파일이 클수록 비율↑). `Compression=none`으로 끌 수 있다.

**짧은 유지보수 주기 + 병렬 업로드.** 한 유지보수 루프가 **compress → upload → reap**을 순서대로 돌리되 주기를 짧게(기본 30s) 잡아, 업로드·disk-cap 검사가 자주 일어나 물리 디스크를 보호한다. 업로드는 `UploadConcurrency`(기본 4)만큼 병렬로 올려 단일 스트림 천장을 넘긴다.

상태 머신: `active → pending(평문) → compressed(.jsonl.gz) → uploaded(+S3)`. 디렉토리 간 이동은 원자적 rename이라, 각 단계가 서로의 중간 상태를 보지 않는다.

## 근거

- 시간 정렬 버킷은 `dt/hour` 파티션과 1:1로 맞아 분석·프루닝이 자명하다.
- 압축은 여기서 가장 값싼 레버다 — 코드 몇 줄, 의존성 0, 두 병목 동시 완화.
- 유지보수 주기를 짧게+병렬로 두면, 앞의 세 천장(처리량·디스크·업로드)이 모두 설정 가능한 상한으로 바뀐다.
- shared-nothing이라 스케일 아웃은 선형 유지(레플리카별 pod명 키, 조율 없음 — [ADR 007](007-audit-result-sink.md)).

## 결과

- **주기 모델**: 로테이션(시간창, 기본 1h 클록정렬) · 유지보수(기본 30s: compress+upload+reap) · retention(기본 7d) · disk-cap(유지보수마다). 크기(128Mi)는 안전판.
- 압축 CPU 비용이 생긴다(gzip ~50–150 MB/s/core). **압축은 의도적으로 단일 코어**(shipper 고루틴 1개)로 둔다 — best-effort 백그라운드 작업이 요청 처리 코어를 뺏으면 안 되므로 병렬화하지 않는다. 반대로 업로드는 I/O 바운드라 병렬화한다. 압축이 병목이 되면 코덱 교체(이미 의존성에 있는 zstd, 코어당 처리량↑)가 병렬화보다 먼저다.
- 이미 압축된 페이로드(이미지 base64)는 압축 이득이 작다 — 텍스트 완성 비중이 높을수록 이득이 크다.
- 지속 무손실 처리량 ≈ `min(워커, 업로드 단일스트림×동시성, DiskCap/UploadInterval)` × 압축비. 튜닝 레버가 명확해졌다.
