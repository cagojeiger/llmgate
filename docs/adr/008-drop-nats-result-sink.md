# ADR 008: NATS 결과 싱크를 제거하고 파일 싱크로 단일화한다

- Status: Accepted
- Date: 2026-08-17
- 관련: 001, 007

## 문제

[ADR 007](007-audit-result-sink.md)은 audit 파일 싱크와 NATS publisher를 fan-out으로 **공존**시켜, 기존 NATS 소비자를 유지한 채 파일 싱크를 도입하도록 했다.

그러나 확인 결과 **NATS `LLMRESULT` 스트림을 실제로 소비하는 것이 없다**. 아무도 읽지 않는 스트림에 계속 발행하는 셈이다. 동시에 인프라를 오사카 리전(OKE)에서 홈 클러스터로 이전하려는데, stateful 브로커는 이전 부담(스트림 재생성, NATS 클러스터 구동, 용량 계획)을 키운다.

"트래픽이 커지면 스트리밍이 낫지 않나"라는 물음도 검토했다 — 결론은, 무엇이 필요한지를 가르는 건 트래픽 양이 아니라 **접근 패턴**이다. 쓰기 버스트 흡수는 로컬 append(파일 싱크)가 오히려 강하고, NATS의 고유 가치는 **소비자에게의 실시간 전달**이다. 실시간 소비자가 없으면 그 가치는 실현되지 않는다.

## 결정

**NATS 결과 싱크를 제거하고, 결과 싱크를 파일 싱크 하나로 둔다.** publisher 패키지, NATS 관련 config·검증, docker-compose의 nats/nats-init, `nats.go` 의존성을 모두 제거한다. 조립기는 `audit` 팩토리 하나만 갖고, 결과 파이프라인은 `Async(FileSink)`로 자연 붕괴한다.

**단, 팩토리 레지스트리와 제네릭 `sinkutil.Fanout`은 남긴다.** 이것들은 얇고 공짜이며, 실시간 소비자가 생겨 NATS(또는 다른 스트리밍 싱크)가 필요해지면 **factory 한 줄 + publisher만 되살려 부활**할 수 있는 확장점이다(코드는 git history에 있다).

## 근거

- **YAGNI**: 소비자가 없는 발행 경로는 순비용이다.
- **이전 부담 감소**: 브로커리스가 되어, 홈 클러스터로 옮길 때 옮길 stateful 서비스가 없다 — S3 엔드포인트(`LLMGATE_AUDIT_S3_ENDPOINT`)만 repoint하면 된다([ADR 007](007-audit-result-sink.md)의 "상태는 오브젝트 스토리지에 위임" 기조와 일치).
- 파일→S3는 고쓰기throughput + 저비용 아카이브에 맞고, 스케일 병목(업로드 병렬도)은 파일 싱크 안에서 개선 가능하다.
- 되돌릴 여지를 코드 구조로 남겼다 — 결정은 문을 닫지 않는다.

## 결과

- 실시간으로 LLM 이벤트를 구독·반응하는 소비자가 필요해지면 NATS(또는 다른 스트리밍 싱크)를 **다시 붙여야** 한다. 골격은 남겼으니 부활 비용은 작다.
- 파일 싱크가 유일 경로이므로, 대규모에서의 업로드 병렬화가 향후 개선 과제로 남는다([ADR 007](007-audit-result-sink.md) 결과의 유실·디스크캡 정책이 그대로 적용).
- 이 변경은 **코드 구조 완성**까지이며, 릴리즈/배포는 별도다 — 배포 토폴로지 이전(오사카→홈)과 S3 프로비저닝이 정리된 뒤에 릴리즈한다.
- `LLMGATE_LLMRESULT_ASYNC_*` env는 이제 파일 싱크의 비동기 경계를 설정한다(이름은 유지, 의미는 결과 싱크 일반).
